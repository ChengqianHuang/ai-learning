# Agent 状态

Agent 的运行状态回答三个问题。**哪些操作已确认完成，哪些操作的结果还未知，接下来允许执行什么。** 进程退出后，新执行者应能根据持久化状态继续处理，并在必要时向外部系统核对结果。

## 1. 状态记录的层次

| 层次 | 表示什么 | 需要保存的信息 |
|---|---|---|
| 任务 | 用户要达成的目标，可跨进程或会话继续 | 任务 ID、目标、约束、完成条件和总预算 |
| 运行 | 一次有开始时间和预算的执行过程 | 运行 ID、触发原因、截止时间和结束原因 |
| 步骤 | 执行计划中的一项工作 | 步骤 ID、依赖、当前状态、完成证据及所属计划版本 |
| 业务操作 | 一次具有明确意图的外部动作 | 稳定的操作 ID、目标资源、参数、幂等键和远端结果标识 |
| 请求尝试 | 对工具或外部接口发出的一次请求 | 尝试 ID、关联的操作 ID、时间、错误码和观测结果 |

同一业务操作可以在恢复后再次发起请求。每次请求用新的尝试 ID，业务操作 ID 保持一致。调用超时首先说明**这次尝试没有及时收到结果**。业务操作是否完成，要由远端状态或接口返回的证据判定。

任务进度、模型上下文和跨任务记忆有各自的生命周期。状态由执行器更新，并作为恢复的依据。上下文每轮按需组装，可以只携带当前步骤和相关证据。跨任务记忆保存未来任务可能用到的信息。模型生成的进度摘要可以帮助理解任务，关键状态仍以持久化记录为准。

## 2. 用状态机约束执行

步骤状态应直接决定调度器允许什么动作。外部操作较多时，把等待、重试和结果未知分开建模。

| 步骤状态 | 可执行的动作 |
|---|---|
| 等待依赖 | 等前置步骤通过完成条件，再进入就绪状态 |
| 就绪 | 由执行者领取，准备调用 |
| 执行中 | 等待本次尝试结束，同时记录执行归属和超时信息 |
| 等待重试 | 到达下次执行时间后，依据剩余预算和工具契约再次尝试 |
| 待核对 | 对已发出但结果未知的操作先核对外部状态，或按已有幂等契约恢复 |
| 阻塞 | 保存缺少的信息、权限或确认条件，条件满足后重新调度 |
| 完成 | 保存可核验的结果，下游步骤可以读取 |
| 失败 | 保存失败原因、已确认的部分结果和终止条件 |

步骤完成与任务结束要分别判断。只有满足任务完成条件，才能报告完整成功。预算耗尽、主动暂停或取消也可以结束本轮运行，任务仍可能保留未完成步骤。取消时先停止分派新步骤，再处理在途操作。远端是否取消，应根据远端返回或查询结果记录。

## 3. 在什么时点持久化

1. **发出调用前保存操作意图。** 写入步骤 ID、操作 ID、目标资源、确定后的参数或其受控引用，以及幂等键。恢复时读取已保存的意图，避免重新生成参数后把同一操作变成另一条请求。
2. **调用结束后保存观测结果。** 记录请求尝试的结局，以及工具返回的资源 ID、状态或错误。收到异步受理回执时保存远端操作 ID，并等到可验证的最终结果再推进步骤。
3. **确认完成时推进状态。** 在本地事务中同时保存结果证据和更新步骤状态。依赖该结果的后续步骤应在事务提交后再调度。

本地数据库事务能保护本地记录的一致性。外部接口通常独立提交，因此从「远端已经执行」到「本地记录完成」之间存在故障窗口。恢复设计要覆盖这个窗口。 [幂等 API 中的服务端提交与重试](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)

## 4. 超时与重启后如何恢复

SQLite 实验可以在检索证据提交后退出进程，再从检查点继续执行。 [状态恢复实验](../agent-practice/README.md#实验二-状态恢复与跨任务记忆)

| 已知事实 | 恢复动作 |
|---|---|
| 步骤已完成，结果证据已保存 | 读取已保存的结果，继续执行依赖它的步骤 |
| 操作意图已保存，能确认请求尚未发出 | 按已保存的参数和标识发出请求 |
| 请求可能已发出，本地缺少最终结果 | 进入待核对。按远端操作 ID 或业务标识查询，或按目标接口的幂等契约用相同键和参数重试 |
| 已确认操作未执行，且失败原因可恢复 | 在剩余预算内重试，另记一次请求尝试 |
| 无法确认结果，接口也缺少可靠的查询与去重能力 | 保留待核对状态，等待进一步证据，避免重复写入 |

重启后看到「执行中」，只能确认它曾被领取。只有能证明请求未发出的情况下，才按首次调用处理。查询时也要看服务的可见性保证。查询接口存在延迟时，暂时查不到记录仍可能是结果未知。

## 5. 并发接管与重复执行

多个执行者竞争同一步骤时，可以用数据库的条件更新领取。领取时核对步骤仍处于可执行状态，并为本次领取记录一个版本号。写回结果时再核对版本，避免已经失去执行权的进程覆盖新状态。

长任务可以使用租约和心跳。租约过期后，新的执行者可以取得本地处理权，但原请求仍可能在远端继续。**领取版本保护的是本地状态，目标接口的幂等键或远端核对保护的是外部结果。** 目标接口的去重范围、有效期和参数约束会影响恢复策略。 [调用方操作标识与幂等重试](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)

## 6. 快照、事件和执行框架

| 方式 | 适用场景 | 需要考虑的代价 |
|---|---|---|
| 状态表和尝试记录 | 从最近的持久化进度恢复，按任务或步骤查询 | 应用要写清状态转换及需要保留的历史 |
| 事件日志与快照 | 需要解释每次状态变化，或从事件重建执行状态 | 要管理事件顺序、数据版本、重放和历史增长 |

普通服务可以先用任务表、步骤表和独立的请求尝试记录。多步骤长任务还可以交给支持持久化执行的框架。使用事件历史的框架会在恢复时重建工作流状态，并复用历史中已经记录的结果。模型调用和外部工具调用都可能返回不同结果，应在工作流记录中保存其结果。远端动作已发生、框架尚未记录完成时，调用仍可能被重试，业务操作依然需要幂等或结果核对。 [Temporal 持久化执行](https://docs.temporal.io/durable-execution)

## 7. 状态设计的验收条件

- 任意步骤中断后，可以判断哪些结果已确认，哪些操作仍待核对。
- 重试沿用原业务操作标识，并留下独立的尝试记录。
- 两个执行者竞争或旧执行者延迟返回时，旧结果无法无条件覆盖较新的本地状态。
- 远端已完成、本地未落盘时，恢复路径依赖已验证的查询或幂等契约，缺少证据时进入待核对。
- 用户取消、任务成功、部分完成和未知结果在记录中能分辨，最终报告与可验证的事实一致。
