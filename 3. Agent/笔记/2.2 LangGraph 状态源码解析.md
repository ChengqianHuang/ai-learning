# 2.2 LangGraph 状态源码解析

## LangGraph 是什么

**LangGraph 是一个用于构建有状态工作流和 Agent 的开源编排框架。** 应用把流程定义成图。**状态**是各步骤共享的数据，**节点**是执行计算、调用模型或使用工具的步骤，**边**决定执行路径。节点读取状态并提交更新，LangGraph 负责调度节点和合并更新。固定工作流和由模型参与决策的 Agent 都可以在这套运行机制上实现。 [LangGraph 官方概览](https://docs.langchain.com/oss/python/langgraph/overview)

## 本篇读的是哪一层

本篇读的是 **Python 实现中图的执行和恢复**。先分清构图、执行和存储各由谁负责。

| 部分 | 职责 |
|---|---|
| `StateGraph` | 应用用它定义状态结构、节点和边。调用 `compile()` 得到可运行的 `CompiledStateGraph`。 |
| `Pregel` | `CompiledStateGraph` 继承的运行时。它按轮次调度节点、收集输出，并把更新应用到图状态。 |
| `checkpointer` | 运行时使用的检查点保存器，负责读写检查点和节点的中间输出。同一个 `thread_id` 可以把多次图调用接在同一条执行历史上。 |

## 状态机制综述

运行时用内部**通道**承载图状态和调度信号。检查点记录通道的值和版本，以及各节点已经见过的版本。恢复时，运行时根据这些记录还原数据，并判断哪些节点该进入下一轮。 [检查点结构](https://github.com/langchain-ai/langgraph/blob/c6335a4255dc1d8abc25a7677f9c072c7ab27b9c/libs/checkpoint/langgraph/checkpoint/base/__init__.py#L93-L124) · [按通道版本判断节点触发](https://github.com/langchain-ai/langgraph/blob/c6335a4255dc1d8abc25a7677f9c072c7ab27b9c/libs/langgraph/langgraph/pregel/_algo.py#L598-L614)

1. **加载图状态。** 配置 checkpointer 后，运行时按线程读取已有检查点和关联的节点写入。需要跨进程恢复时，checkpointer 的存储也要在进程退出后存续。
2. **按轮次调度节点。** LangGraph 把一轮调度称为 `superstep`。同一轮可以执行多个节点，各节点提交自己的更新。轮次完成时，执行器按通道规则应用这些更新，再推进图的检查点。 [一轮结束时应用写入](https://github.com/langchain-ai/langgraph/blob/c6335a4255dc1d8abc25a7677f9c072c7ab27b9c/libs/langgraph/langgraph/pregel/_loop.py#L742-L750)
3. **保存整轮状态，也能保存单个节点的写入。** 检查点对应一轮的状态边界。逐步持久化时，已经成功的节点可以先把输出写进 `pending_writes` 对应的持久化记录。即使同轮另一个节点失败，恢复时也有机会复用这些已落盘的结果。
4. **从图的边界继续。** 恢复先重建检查点里的通道，再应用可复用的节点写入。失败或中断的节点可能重新执行。用 `interrupt()` 暂停时，恢复会从被中断节点的入口重跑，走到中断点才拿到恢复值。节点里的外部写入仍要单独设计幂等或结果核对。

读下面的源码时，可以顺着 **加载检查点 → 调度节点 → 保存节点写入 → 应用更新并推进检查点** 这条主线。**能恢复一轮图状态**和**能复用某个节点的输出**分别对应检查点和已保存的节点写入。

## 检查点记录了什么

配置 checkpointer 后，图运行用 `thread_id` 找到同一执行线程。源码里的 `Checkpoint` 包含 `channel_values`、`channel_versions` 和 `versions_seen`。它们分别记录图中各通道的值、通道版本，以及各节点已经看到的版本。执行器用这些信息重建通道并决定哪些节点该运行。`CheckpointTuple` 还带 `pending_writes`，用于保存与该检查点关联的节点写入。跨线程的长期记忆由独立的 Store 按应用需要读写。 [检查点数据结构](https://github.com/langchain-ai/langgraph/blob/c6335a4255dc1d8abc25a7677f9c072c7ab27b9c/libs/checkpoint/langgraph/checkpoint/base/__init__.py#L93-L147) · [读取检查点](https://github.com/langchain-ai/langgraph/blob/c6335a4255dc1d8abc25a7677f9c072c7ab27b9c/libs/langgraph/langgraph/pregel/_loop.py#L1886-L1932) · [Checkpointer 与 Store](https://docs.langchain.com/oss/python/langgraph/persistence)

## 同一轮有节点成功、有节点失败

一个 **superstep** 是图调度的一轮。同一轮内可运行多个节点。配置逐步持久化时，`put_writes()` 可先把已完成节点的输出写到当前检查点关联的记录里。整轮结束时，执行器再推进图的检查点。

使用持久化 checkpointer 时，`durability="sync"` 会等待检查点写入再进入下一轮，`"async"` 可与下一轮并行保存，`"exit"` 则在图退出时持久化。进程异常退出后的恢复点取决于哪些写入已经完成。 [固定版本的持久化模式](https://github.com/langchain-ai/langgraph/blob/c6335a4255dc1d8abc25a7677f9c072c7ab27b9c/libs/langgraph/langgraph/pregel/main.py#L2817-L2822)

正常恢复时，`_reapply_writes_to_succeeded_nodes()` 把已持久化的成功输出装回对应任务。这样即使同轮另一个节点失败，已保存结果的节点也可以跳过。失败或中断的节点则可能重跑，或进入配置好的错误处理分支。这个行为依赖写入已经保存以及以普通恢复方式加载。 [记录节点写入](https://github.com/langchain-ai/langgraph/blob/c6335a4255dc1d8abc25a7677f9c072c7ab27b9c/libs/langgraph/langgraph/pregel/_loop.py#L532-L558) · [整轮推进检查点](https://github.com/langchain-ai/langgraph/blob/c6335a4255dc1d8abc25a7677f9c072c7ab27b9c/libs/langgraph/langgraph/pregel/_loop.py#L780-L786) · [恢复已完成节点的输出](https://github.com/langchain-ai/langgraph/blob/c6335a4255dc1d8abc25a7677f9c072c7ab27b9c/libs/langgraph/langgraph/pregel/_loop.py#L847-L878)

## Interrupt 恢复会从节点入口重跑

节点执行 `interrupt()` 可以暂停等待外部输入。恢复时用同一个 `thread_id` 和 `Command(resume=...)` 传回答复。**被中断的节点从函数开头重新执行**，重新走到 `interrupt()` 时才获得恢复值。中断前的逻辑因此可能再执行一遍。如果有外部写入，可以把确认与写入放到不同节点，或让写入支持幂等。 [Interrupt 源码](https://github.com/langchain-ai/langgraph/blob/c6335a4255dc1d8abc25a7677f9c072c7ab27b9c/libs/langgraph/langgraph/types.py#L913-L939) · [暂停与恢复语义](https://docs.langchain.com/oss/python/langgraph/interrupts)

## 与 OpenHands SDK 对照恢复边界

下表对照两条执行路径。2.1 看的是 OpenHands 内置 Agent 的本地会话，2.2 看的是 LangGraph 通用图运行时。 [2.1 OpenHands SDK 状态源码解析](2.1%20OpenHands%20SDK%20状态源码解析.md)

| 要看什么 | OpenHands SDK | LangGraph |
|---|---|---|
| 恢复入口 | 会话 ID 对应的基础状态和事件日志 | `thread_id` 对应的图检查点及其节点写入 |
| 判断已处理的证据 | 当前分支上能与动作配对的结果事件 | 已持久化并能复用的成功节点输出 |
| 可能重新执行的单位 | 缺少结果事件的工具动作 | 中断或失败且需要重跑的节点 |
| 外部写入已发生而本地尚未记账 | 动作仍可能显示为待处理 | 节点仍可能缺少可复用的输出 |

读其他 Agent 的源码时，先找**恢复入口、完成证据和重新执行的最小单位**。这三处能确定进程重启后哪些结果可复用，哪些副作用需要另外核对。
