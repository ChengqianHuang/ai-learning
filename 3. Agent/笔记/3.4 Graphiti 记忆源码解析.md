# 3.4 Graphiti 记忆源码解析

## Graphiti 是什么

**Graphiti 是用于构建和查询时序知识图谱的开源 Python 库。** 应用把消息、文档或结构化数据交给它。Graphiti 抽取实体及关系，把关系和来源事件关联起来，并为关系记录时间信息。它适合研究一条事实何时成立、何时失效，以及从哪里得到。 [Graphiti 开源仓库](https://github.com/getzep/graphiti) · [Episode 的定义](https://help.getzep.com/graphiti/core-concepts/adding-episodes)

## 本篇读的是哪一层

本篇固定到提交 `a61333e`，追踪 `graphiti_core` 里 `Graphiti.add_episode()` 的默认写入路径和 `Graphiti.search()` 的基础边检索。这里读的是并发摄取关闭时的单次写入。重点是关系如何形成、冲突如何影响有效期、查询如何区分当前事实与历史事实。应用负责选择何时写入资料，以及如何消费查询结果。 [写入入口](https://github.com/getzep/graphiti/blob/a61333edfa14cc483365ed7dd1e287ae6096db6c/graphiti_core/graphiti.py#L1630-L1649) · [写入路径分支](https://github.com/getzep/graphiti/blob/a61333edfa14cc483365ed7dd1e287ae6096db6c/graphiti_core/graphiti.py#L1731-L1775) · [检索入口](https://github.com/getzep/graphiti/blob/a61333edfa14cc483365ed7dd1e287ae6096db6c/graphiti_core/graphiti.py#L2316-L2375)

## 记忆机制综述

应用提交一个 **episode**，即一次有来源和参考时间的数据输入。Graphiti 结合相关的早期输入，把新内容里的实体对齐到图里的节点，再提取和解析关系边。已经存在的关系可以增加来源，发生矛盾的关系则按时间判断该结束哪一条。检索时用关键词和向量召回关系边，返回给应用做后续处理。 [常规写入链路](https://github.com/getzep/graphiti/blob/a61333edfa14cc483365ed7dd1e287ae6096db6c/graphiti_core/graphiti.py#L1771-L1895) · [默认召回配置](https://github.com/getzep/graphiti/blob/a61333edfa14cc483365ed7dd1e287ae6096db6c/graphiti_core/search/search_config_recipes.py#L111-L116)

| 图里的对象 | 代表什么 | 读取时怎么用 |
|---|---|---|
| `EpisodicNode` | 一次输入及其来源、参考时间 | 追溯信息由哪次录入产生 |
| `EntityNode` | 图中可以被多次提及的对象 | 将来自不同输入的信息归到同一实体 |
| `EntityEdge` | 两个实体之间的一条关系事实，含事实文本和时间字段 | 直接召回关系，并判断在目标时间是否成立 |
| `group_id` | 图数据的分组标识 | 把写入和查询限定在应用选定的范围 |

## 写入从哪一步变成图数据

1. **读取同一分组的相关历史。** 常规 `add_episode()` 用输入的 `reference_time` 查早期 episode，也允许应用明确提供前序 episode ID。新 episode 保存参考时间和录入时间，为提取和追溯提供两个时间点。 [获取早期事件与构造新事件](https://github.com/getzep/graphiti/blob/a61333edfa14cc483365ed7dd1e287ae6096db6c/graphiti_core/graphiti.py#L1771-L1805)
2. **提取实体并完成对齐。** `extract_nodes()` 先从输入识别候选实体。`resolve_extracted_nodes()` 再检索图中的候选，用身份属性规则、相似度规则或 LLM 决定是否复用已有节点，并建立从临时实体到已解析实体的 ID 映射。错误合并会使后续关系挂到错误的对象上，因此实体对齐是独立的质量问题。 [实体提取入口](https://github.com/getzep/graphiti/blob/a61333edfa14cc483365ed7dd1e287ae6096db6c/graphiti_core/graphiti.py#L1814-L1849) · [实体解析](https://github.com/getzep/graphiti/blob/a61333edfa14cc483365ed7dd1e287ae6096db6c/graphiti_core/utils/maintenance/node_operations.py#L844-L923)
3. **提取关系并关联来源。** 提取出来的边先用上一步的 ID 映射修正端点，再交给解析器与图中的边比对。写入阶段会保存 episode、实体、关系边，以及指向相关实体的提及记录。`EntityEdge.episodes` 也保存引用该边的 episode ID。原文能否直接回看取决于 `store_raw_episode_content` 是否保留正文。 [解析边的入口](https://github.com/getzep/graphiti/blob/a61333edfa14cc483365ed7dd1e287ae6096db6c/graphiti_core/graphiti.py#L1094-L1134) · [保存 episode 与图变更](https://github.com/getzep/graphiti/blob/a61333edfa14cc483365ed7dd1e287ae6096db6c/graphiti_core/graphiti.py#L1178-L1196) · [边的来源字段](https://github.com/getzep/graphiti/blob/a61333edfa14cc483365ed7dd1e287ae6096db6c/graphiti_core/edges.py#L228-L255)

## 图里出现矛盾时怎样保存历史

关系解析把**重复**和**矛盾**分开判断。端点相同且规范化后的事实文本相同时，可以直接复用旧边并追加 episode 来源。其他情况下，程序给 LLM 提供重复和矛盾候选，校验模型返回的候选编号，再应用时间规则。矛盾候选来自相似事实召回，因此发现冲突的能力依赖候选覆盖和识别质量。 [矛盾候选检索](https://github.com/getzep/graphiti/blob/a61333edfa14cc483365ed7dd1e287ae6096db6c/graphiti_core/utils/maintenance/edge_operations.py#L552-L579) · [重复与矛盾判定](https://github.com/getzep/graphiti/blob/a61333edfa14cc483365ed7dd1e287ae6096db6c/graphiti_core/utils/maintenance/edge_operations.py#L928-L1014) · [精确重复边追加来源](https://github.com/getzep/graphiti/blob/a61333edfa14cc483365ed7dd1e287ae6096db6c/graphiti_core/utils/maintenance/edge_operations.py#L1076-L1124)

| 字段 | 回答的问题 |
|---|---|
| `valid_at` | 这条事实从什么时候成立 |
| `invalid_at` | 这条事实从什么时候停止成立 |
| `expired_at` | Graphiti 是什么时候将它标记为失效的 |

对判定为矛盾、且时间区间有重叠的边，代码按生效时间确定失效方向。较晚生效的事实可以截止较早那条。迟到录入的旧事实也可能被已有的较晚事实截止。失效边随结果一起写回图，历史事实仍可用于查询。**录入顺序和事实生效顺序可以不同。** [时间字段的定义](https://github.com/getzep/graphiti/blob/a61333edfa14cc483365ed7dd1e287ae6096db6c/graphiti_core/edges.py#L236-L252) · [应用时间冲突规则](https://github.com/getzep/graphiti/blob/a61333edfa14cc483365ed7dd1e287ae6096db6c/graphiti_core/utils/maintenance/edge_operations.py#L762-L830) · [包含失效边的保存流程](https://github.com/getzep/graphiti/blob/a61333edfa14cc483365ed7dd1e287ae6096db6c/graphiti_core/graphiti.py#L1870-L1895)

## 检索如何区分当前事实和历史事实

基本 `search()` 默认以 BM25 和向量相似度各自召回关系边，再用 RRF（按名次融合）合并排名。有 `center_node_uuid` 时，可以按图距离重排。搜索输出是带来源与时间字段的 `EntityEdge` 列表，应用可以进一步筛选后再注入模型。 [查询配置选择](https://github.com/getzep/graphiti/blob/a61333edfa14cc483365ed7dd1e287ae6096db6c/graphiti_core/graphiti.py#L2358-L2375) · [两路召回与 RRF](https://github.com/getzep/graphiti/blob/a61333edfa14cc483365ed7dd1e287ae6096db6c/graphiti_core/search/search.py#L289-L307) · [融合排名](https://github.com/getzep/graphiti/blob/a61333edfa14cc483365ed7dd1e287ae6096db6c/graphiti_core/search/search.py#L377-L383)

**检索相关和在某个时间有效需要分别判断。** 基础入口未传筛选器时使用默认的 `SearchFilters()`，其中各日期条件为空。若要回答时点 `t` 的事实，对已知生效时间的边可以要求 `valid_at ≤ t`，并且 `invalid_at` 为空或晚于 `t`。日期缺失时按应用的证据政策处理，并为需要隔离的数据显式传入授权的 `group_ids`。 [日期字段与查询运算符](https://github.com/getzep/graphiti/blob/a61333edfa14cc483365ed7dd1e287ae6096db6c/graphiti_core/search/search_filters.py#L27-L65) · [日期如何进入过滤条件](https://github.com/getzep/graphiti/blob/a61333edfa14cc483365ed7dd1e287ae6096db6c/graphiti_core/search/search_filters.py#L156-L216) · [图分组说明](https://help.getzep.com/graphiti/core-concepts/graph-namespacing)

## 接入时如何选择

如果问题主要是「取回相关的偏好、经验或约定」，可以先看 Mem0 的条目提取和查询。如果问题还需要「同一实体有多条关系，哪条在指定时间成立，证据来自哪里」，Graphiti 的图结构和时间字段才有用。使用图结构也会引入实体对齐、关系抽取和时间冲突的判断成本。 [3.3 Mem0 记忆源码解析](3.3%20Mem0%20记忆源码解析.md)
