# 3.2 LangGraph 记忆源码解析

## LangGraph 是什么

**LangGraph 是用于构建有状态工作流和 Agent 的开源编排框架。** 应用定义节点和执行路径，运行时调度节点并合并状态更新。节点要不要调用模型、读哪些记忆、把哪些内容发给模型，取决于应用在节点和中间件里定义的逻辑。 [LangGraph 官方概览](https://docs.langchain.com/oss/python/langgraph/overview)

## 本篇读的是哪一层

本篇沿 Python `StateGraph` 编译后的调用路径，追踪三件事。线程内历史如何随图状态恢复，跨线程条目如何通过 `BaseStore` 读写，以及两类数据如何进入模型请求。源码固定在提交 `c6335a4`，图恢复的调度细节见 [2.2 LangGraph 状态源码解析](2.2%20LangGraph%20状态源码解析.md)。

## 记忆机制综述

| 环节 | 谁负责 | 决定什么 |
|---|---|---|
| 恢复线程状态 | 图运行时和 `checkpointer` | 从同一个 `thread_id` 继续，恢复状态里已有的消息和其他字段 |
| 读写跨线程记忆 | 节点或应用通过 Store 接口操作 | 用 `namespace` 和 `key` 定位条目，或在指定范围里检索 |
| 组装模型输入 | 调用模型的节点或中间件 | 从当前消息和检索结果中选择要发给模型的内容 |
| 保存新信息 | 图运行时保存节点返回的状态更新，应用决定是否写入 Store | 一次回复可以只更新当前线程，也可以按规则更新某个跨线程条目 |

LangGraph 官方把线程内的这部分用法称为短期记忆，把跨线程 Store 称为长期记忆。**短期和长期在这里描述访问范围。** 线程状态可以借助持久化 checkpointer 保存很久，跨线程条目也可以暂时只存在进程内。记录在磁盘上能否恢复，以及内容有没有进入本轮模型输入，仍要分别判断。 [Checkpointer 与 Store 对比](https://docs.langchain.com/oss/python/langgraph/persistence#checkpointer-vs-store)

## 线程内记忆如何恢复和更新

配置 `checkpointer` 后，`SyncPregelLoop` 调用 `get_tuple()` 读取当前线程的检查点，通过 `channels_from_checkpoint()` 恢复通道。应用如果用 `MessagesState`，`messages` 就是随图状态保存的一个字段。同一线程的后续调用可以读到已保存的消息，也可以继续使用此前保存的任务数据。 [检查点加载与通道恢复](https://github.com/langchain-ai/langgraph/blob/c6335a4255dc1d8abc25a7677f9c072c7ab27b9c/libs/langgraph/langgraph/pregel/_loop.py#L1886-L1932) · [MessagesState 定义](https://github.com/langchain-ai/langgraph/blob/c6335a4255dc1d8abc25a7677f9c072c7ab27b9c/libs/langgraph/langgraph/graph/message.py#L320-L321)

`MessagesState` 为消息字段指定了 `add_messages` 合并规则。它追加新 ID 的消息，按 ID 替换已有消息，并处理 `RemoveMessage`。这解释了为什么节点可以只返回一条新消息，下一轮仍能读到合并后的历史。如果节点只裁剪临时传给模型的消息列表，保存的历史不会随之缩短。要改变当前线程状态，需要把变更提交为图状态更新。留存的旧检查点还要按保存策略另行处理。 [消息合并实现](https://github.com/langchain-ai/langgraph/blob/c6335a4255dc1d8abc25a7677f9c072c7ab27b9c/libs/langgraph/langgraph/graph/message.py#L191-L243) · [官方历史管理说明](https://docs.langchain.com/oss/python/langgraph/add-memory#manage-short-term-memory)

## Store 如何交给节点

`StateGraph.compile()` 接收 `checkpointer` 和 `store` 两个参数，并分别交给 `CompiledStateGraph`。同步运行时创建 `Runtime`，把 Store 实例放进 `Runtime.store`。执行节点时，`RunnableCallable.invoke()` 从运行配置里取出这个 `Runtime`，按节点接受的参数注入。到这一步，节点获得的是可调用的存储接口。具体的 `get()`、`search()` 和 `put()` 由节点或应用发起。 [编译时传入两个对象](https://github.com/langchain-ai/langgraph/blob/c6335a4255dc1d8abc25a7677f9c072c7ab27b9c/libs/langgraph/langgraph/graph/state.py#L1346-L1368) · [构建 Runtime](https://github.com/langchain-ai/langgraph/blob/c6335a4255dc1d8abc25a7677f9c072c7ab27b9c/libs/langgraph/langgraph/pregel/main.py#L2985-L2995) · [节点参数注入](https://github.com/langchain-ai/langgraph/blob/c6335a4255dc1d8abc25a7677f9c072c7ab27b9c/libs/langgraph/langgraph/_internal/_runnable.py#L424-L443)

### 条目怎样定位和更新

`Item` 由层级命名空间 `namespace`、命名空间内唯一的 `key`、字典形式的 `value` 和时间戳组成。`get()` 用完整的 `(namespace, key)` 读取单条，`put()` 把同样的组合和新值包装成 `PutOp` 交给后端。在 `InMemoryStore` 中，写入是对这个组合做整条赋值。字段合并、版本冲突和重复记忆怎么处理，需要由应用或所选存储实现定义。跨线程复用时，各线程在共享的 Store 后端访问同一批条目。命名空间用于组织和定位数据，对应的用户或工作区访问权限由应用校验。 [Item 定义](https://github.com/langchain-ai/langgraph/blob/c6335a4255dc1d8abc25a7677f9c072c7ab27b9c/libs/checkpoint/langgraph/store/base/__init__.py#L51-L88) · [写入接口](https://github.com/langchain-ai/langgraph/blob/c6335a4255dc1d8abc25a7677f9c072c7ab27b9c/libs/checkpoint/langgraph/store/base/__init__.py#L866-L912) · [内存后端取值和赋值](https://github.com/langchain-ai/langgraph/blob/c6335a4255dc1d8abc25a7677f9c072c7ab27b9c/libs/checkpoint/langgraph/store/memory/__init__.py#L396-L425)

### 筛选与语义检索怎样配合

`search()` 接收命名空间前缀、`filter`、`query`、`limit` 和 `offset`，封装成 `SearchOp` 交给后端。`InMemoryStore` 先沿命名空间前缀收集候选，再按 `value` 中的字段应用筛选条件。配置了嵌入且有 `query` 时，后端把查询向量与候选向量算余弦相似度，并按得分返回条目。写入侧可按配置选取要嵌入的字段。其他后端的检索能力与排序要看各自实现。 [查询接口](https://github.com/langchain-ai/langgraph/blob/c6335a4255dc1d8abc25a7677f9c072c7ab27b9c/libs/checkpoint/langgraph/store/base/__init__.py#L784-L811) · [候选过滤与查询嵌入](https://github.com/langchain-ai/langgraph/blob/c6335a4255dc1d8abc25a7677f9c072c7ab27b9c/libs/checkpoint/langgraph/store/memory/__init__.py#L238-L294) · [相似度排序与返回](https://github.com/langchain-ai/langgraph/blob/c6335a4255dc1d8abc25a7677f9c072c7ab27b9c/libs/checkpoint/langgraph/store/memory/__init__.py#L317-L382)

这里有一个容易误判的细节。在这个版本的 `InMemoryStore` 中，未配置索引时，传入 `query` 仍可能得到结果，走的是过滤后的分页。配置索引时，如果带向量的结果不足，未评分条目也可能被补入，`score` 为 `None`。因此调用方要根据实际检索配置和返回值判断这批内容的含义。 [有评分与无评分的分支](https://github.com/langchain-ai/langgraph/blob/c6335a4255dc1d8abc25a7677f9c072c7ab27b9c/libs/checkpoint/langgraph/store/memory/__init__.py#L348-L382)

## 记忆什么时候进入模型上下文

官方文档的调用路径把读取、写入和组装请求分别放在应用逻辑里。先从 `Runtime.context` 取出用于确定范围的用户标识，再用 `Runtime.store` 取回相关条目，最后由模型调用节点把选定的字段和当前消息组成这次请求。是否提取新记忆、用哪个键写入、是否覆盖原值也由应用规则决定。**同一 `thread_id` 恢复的是图状态，挂载 Store 提供的是存储能力，模型实际收到的是调用节点组装的请求。** [Store 在图中的读写方式](https://docs.langchain.com/oss/python/langgraph/stores#using-in-langgraph)

## 持久化与重放的边界

- `InMemoryStore` 用进程内字典保存数据和可选向量，`InMemorySaver` 用内存保存检查点。跨进程恢复需要分别选择持久化后端。`PostgresStore` 和 `PostgresSaver` 分别负责条目与检查点，可根据所需能力独立配置。 [InMemoryStore 初始化](https://github.com/langchain-ai/langgraph/blob/c6335a4255dc1d8abc25a7677f9c072c7ab27b9c/libs/checkpoint/langgraph/store/memory/__init__.py#L176-L204) · [官方持久化选项](https://docs.langchain.com/oss/python/langgraph/persistence)
- 从源码调用顺序看，节点可以先写入 Store，再返回更新给图运行时。在 Store 已经落盘、节点结果尚未被运行时保存时发生中断，恢复后可能再次执行该节点。对需要幂等的记忆写入，可以由应用选用稳定的 `(namespace, key)` 并定义冲突策略。用同一键覆盖可以避免生成两条记录，还需判断重放的旧值是否允许覆盖新值。 [Store 写入路径](https://github.com/langchain-ai/langgraph/blob/c6335a4255dc1d8abc25a7677f9c072c7ab27b9c/libs/checkpoint/langgraph/store/base/__init__.py#L934-L950) · [图运行时应用节点更新](https://github.com/langchain-ai/langgraph/blob/c6335a4255dc1d8abc25a7677f9c072c7ab27b9c/libs/langgraph/langgraph/pregel/_loop.py#L742-L750)

本文按上述固定提交做源码追踪。中断后重复写入是根据两条写入路径推导的恢复风险，实际结果取决于所选后端与节点的重放行为。
