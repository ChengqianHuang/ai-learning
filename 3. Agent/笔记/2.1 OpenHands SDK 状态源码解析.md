# 2.1 OpenHands SDK 状态源码解析

本篇分析 OpenHands SDK 的一条运行路径：**`LocalConversation` 管理会话和持久化，调用 SDK 内置的 `Agent` 执行一步。** `AgentBase` 定义 Agent 实现需要遵循的接口，`Agent` 是 SDK 提供的主要实现。`LocalConversation` 按 `AgentBase` 接收实现，因此也能运行其他实现。 [SDK Agent 组件说明](https://docs.openhands.dev/sdk/arch/agent) · [运行循环调用 `step()`](https://github.com/OpenHands/software-agent-sdk/blob/53ecc14a8a039faed26fc045b813321bad8e594f/openhands-sdk/openhands/sdk/conversation/impl/local_conversation.py#L2751-L2764)

下文的会话保存和恢复属于 `LocalConversation` 与 `ConversationState`，扫描动作和结果属于内置 `Agent` 的 `_step()` 路径。源码固定在提交 `53ecc14`。

## 状态机制综述

OpenHands 的恢复单位是一场**会话**。一场会话可以多次调用 `run()`。SDK 同时记录两个层次的进度。会话级的 `execution_status` 表示当前是运行、暂停、等待确认还是结束等状态，由 `ConversationState.transition()` 校验更新。工具级的进度则来自事件日志，逐条回答「哪项动作已经有结果」。即使会话重新进入 `RUNNING`，执行器仍要查事件才能知道具体还有什么要做。 [状态转换](https://github.com/OpenHands/software-agent-sdk/blob/53ecc14a8a039faed26fc045b813321bad8e594f/openhands-sdk/openhands/sdk/conversation/state.py#L831-L861) · [运行循环](https://github.com/OpenHands/software-agent-sdk/blob/53ecc14a8a039faed26fc045b813321bad8e594f/openhands-sdk/openhands/sdk/conversation/impl/local_conversation.py#L2670-L2749)

1. **启动或恢复会话。** 启用持久化后，`base_state.json` 保存会话配置、运行状态和当前事件分支的位置，`events/` 保存该会话中发生过的事件。重新打开同一个会话 ID 时，SDK 读入这两部分，再沿当前分支重建可用历史。
2. **决定接下来做什么。** 内置 `Agent` 每一步先检查当前分支里是否有尚未配对的工具动作。有可执行的待处理动作时，先处理它们。否则，从会话视图组装模型上下文，让模型提出新动作或给出回复。
3. **记录动作和结果。** 工具动作先以 `ActionEvent` 进入日志，工具执行后再写入结果事件。后续扫描靠这两类记录配对。配对完成表示动作已经有处理结论，结论可以是成功、失败或拒绝。
4. **从已保存的进度继续。** 会话重启后，已经配对的动作可以直接使用日志里的结果。只有动作记录、缺少结果的操作仍可能被当作待处理并重新执行。外部系统可能已经接受写入，是否可安全再执行要由工具的幂等能力或结果核对来判断。

读下面的源码时，可以顺着 **打开会话 → 读取当前分支 → 找到未配对动作 → 执行并记录结果** 这条主线。`execution_status` 决定会话如何推进，**事件配对**决定工具进度从哪里接上。

## 两份存储如何配合

启用本地持久化时，`ConversationState` 把会话基础状态和事件历史分别存储。`base_state.json` 保存会话 ID、Agent 配置、执行状态和当前分支位置等字段。`EventLog` 把事件逐条写入 `events/`。`LocalConversation` 的默认回调把事件交给 `append_event()`，后者为事件关联父节点、追加日志并按事件类型更新当前分支位置。恢复时，`ConversationState.create()` 先读基础状态，再挂载日志，从当前分支重建视图。 [恢复入口](https://github.com/OpenHands/software-agent-sdk/blob/53ecc14a8a039faed26fc045b813321bad8e594f/openhands-sdk/openhands/sdk/conversation/state.py#L694-L736) · [事件回调](https://github.com/OpenHands/software-agent-sdk/blob/53ecc14a8a039faed26fc045b813321bad8e594f/openhands-sdk/openhands/sdk/conversation/impl/local_conversation.py#L526-L533) · [追加事件](https://github.com/OpenHands/software-agent-sdk/blob/53ecc14a8a039faed26fc045b813321bad8e594f/openhands-sdk/openhands/sdk/conversation/state.py#L485-L507)

`active_branch()` 按当前分支末端追溯父节点。判断待执行动作时，只查看这条路径。Agent 准备下一次模型输入时还会使用视图及可选的 condenser，因此磁盘上的完整历史、当前有效分支和本轮模型上下文是三个不同的范围。 [当前分支](https://github.com/OpenHands/software-agent-sdk/blob/53ecc14a8a039faed26fc045b813321bad8e594f/openhands-sdk/openhands/sdk/conversation/state.py#L416-L423) · [模型输入组装](https://github.com/OpenHands/software-agent-sdk/blob/53ecc14a8a039faed26fc045b813321bad8e594f/openhands-sdk/openhands/sdk/agent/agent.py#L897-L911)

## 源码怎样判定动作已经结束

1. 模型给出的工具调用通过参数解析后，Agent 发出 `ActionEvent`。
2. 执行工具后，Agent 构造 `ObservationEvent`，用 `action_id` 关联原动作。部分工具执行错误会形成 `AgentErrorEvent`。
3. `get_unmatched_actions()` 扫描当前分支。观察结果和用户拒绝按 `action_id` 配对，`AgentErrorEvent` 按 `tool_call_id` 配对。有效动作缺少这几类结果时，才留在待处理列表。进入 `_step()` 的待处理分支时，Agent 先尝试执行这些动作，再返回本轮控制流。

## 恢复边界

从调用顺序可以推断，工具完成外部写入之后、`ObservationEvent` 保存之前如果进程退出，重新读取日志时仍可能只看到 `ActionEvent`。待处理分支可能再次调用该工具。**事件配对能判断日志里有没有结果，外部副作用是否已经发生还要靠工具自身的幂等或核对能力。** 这是源码路径推断，具体结果也受工具和运行配置影响。

仓库里有两类测试适合对照阅读。损坏事件文件的测试断言，读取失败的事件会用错误事件占住原来的 ID，之后会话仍能写入新事件。`rerun_actions()` 的测试走的是显式重执行入口，验证非幂等动作再次执行时会得到错误观察。两者分别检查日志可恢复性和工具重复执行的行为。 [损坏事件测试](https://github.com/OpenHands/software-agent-sdk/blob/53ecc14a8a039faed26fc045b813321bad8e594f/tests/sdk/conversation/local/test_resume_damaged_event_file.py#L37-L68) · [显式重执行测试](https://github.com/OpenHands/software-agent-sdk/blob/53ecc14a8a039faed26fc045b813321bad8e594f/tests/sdk/conversation/local/test_rerun_actions.py#L477-L529)
