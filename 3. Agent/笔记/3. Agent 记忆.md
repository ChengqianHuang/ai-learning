# Agent 记忆

Agent 的记忆机制决定**过去的信息如何在未来的调用里重新生效**。从一条信息被观察到开始，要决定它是否值得保存、在什么范围内有效、什么时候查回来，以及原信息变化后怎么修正。状态专题关心中断后从哪一步继续，本篇关心后续推理能复用哪些信息，以及这些信息还能不能信。

## 1. 上下文、历史、状态与记忆

| 概念 | 主要作用 | 有效范围 |
|---|---|---|
| 模型上下文 | 本次真正发送给模型的消息、指令和资料 | 当前模型调用，有 Token 预算 |
| 会话历史 | 保存消息、工具调用和结果，供回看、压缩和按需提取 | 同一会话或执行线程 |
| 执行状态 | 记录步骤进度、外部操作标识和完成证据，供执行器恢复 | 当前任务或运行 |
| 跨任务记忆 | 保存可以在未来任务中复用的信息 | 按用户、项目或组织明确划定 |

历史和执行状态可以存放在同一个检查点里，未来也可以分别读取。保存到数据库只解决了留存问题。一条历史或记忆要影响模型，还要经过读取、筛选和上下文组装。**同一线程的历史即使保存很久，范围仍是这个线程。** 工程上区分短期和长期记忆，首先看能否跨线程复用，而非存了多少天。 [LangChain 记忆概览](https://docs.langchain.com/oss/python/concepts/memory) · [LangGraph 持久化](https://docs.langchain.com/oss/python/langgraph/persistence)

## 2. 记住什么

按内容可以分成三类，用途会影响保存和更新方式。 [记忆类型与分类](https://docs.langchain.com/oss/python/concepts/memory#long-term-memory)

| 类别 | 保存的内容 | 更新与使用 |
|---|---|---|
| 事实与偏好（语义记忆） | 可描述的事实、已确认的用户偏好、项目约定 | 同一属性用稳定的键管理当前版本。涉及动态事实时保留核验时间 |
| 经验（情节记忆） | 曾完成的任务、关键决策、有效做法和结果证据 | 按目标与条件查回，评估以前的结论对当前任务是否仍适用 |
| 作业规则（程序性记忆） | 可复用的流程、技能和行为约定 | 以适用范围、来源和版本控制变更。影响权限或执行边界的规则由应用管理 |

字段稳定、经常整组读取的偏好，可以集中成一份配置档案。持续积累的经验适合拆成独立条目，以便只取相关部分，并分别更新或撤回。**保存形式和读取方式是两个选择。** 已知逻辑键时可以精确查询，按主题回忆经验时可以使用语义检索。RAG 也使用检索和上下文组装。记忆系统还要处理信息从哪里形成、何时更新和怎样失效。 [档案与条目集合](https://docs.langchain.com/oss/python/concepts/memory#semantic-memory)

## 3. 记忆怎样形成

把写入拆成三个决策。**从观察提取候选，判断能否复用，再按当前记录决定如何更新。** 模型可以提议要保存的条目，应用负责校验归属、来源、权限和数据结构。历史中的临时要求、推测和未经确认的工具输出，应保留它们各自的可信度，避免在后续任务里以已确认事实使用。

| 记录字段 | 解决的问题 |
|---|---|
| 主体、作用域、逻辑键 | 能给谁用，如何识别对同一事实或规则的更新 |
| 内容、类型、来源 | 记住什么，能回到哪条原始消息、文件或观察核对 |
| 生效时间、核验时间、版本 | 信息是否仍适用，冲突或并发更新时如何判断先后 |
| 状态、可见范围 | 当前是否可读，何时失效或撤回 |

写入可以放在**任务执行中**，也可以交给**后台处理**。执行中写入适合需要立即生效的更新，代价是增加当前请求耗时。后台写入可以集中抽取和去重，代价是新记忆生效会有延迟。两种写法都需要处理同一来源重复投递和并发修改。可以按来源标识去重，并用记录版本拒绝基于旧快照的覆盖。 [前台和后台写入](https://docs.langchain.com/oss/python/concepts/memory#writing-memories)

## 4. 记忆怎样进入模型上下文

1. **确定读取范围。** 应用从已认证的用户、当前项目和任务确定可访问的命名空间，过滤失效或撤回的记录。命名空间负责组织记录，访问权限仍由应用控制。
2. **取候选。** 已知属性优先按键读取。主题较开放时可用关键词或语义搜索，先从允许访问的空间里找候选。
3. **决定哪些值得用。** 结合当前问题、来源、时效和适用范围筛选。相似度表示内容接近的程度。事实是否可靠、约定是否仍有效，需要结合版本和来源判断。
4. **按预算组装上下文。** 把当前任务所需的记忆以单独的数据区块交给模型，保留必要的来源和不确定性。当前指令与已记忆的同级偏好冲突时，以当前明确要求为准。高影响或易变的信息，可先向原系统核对。

读取和注入可以发生在调用模型之前，也可以让模型通过读取工具按需召回。前者的使用时机可预期，后者适合推理到中途才发现需要更多背景。两者都要控制读取空间和注入量。 [上下文检索与按需取回](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)

## 5. 长会话如何压缩

同一会话中，模型输入可以保留近期消息，把较早的部分压缩成摘要，并按需回看原文。摘要优先保留目标、关键约束、已确认结论、当前阻塞和重要来源。工具调用与结果应成对保留，或一起转为可追溯的摘要。执行器恢复所需的操作标识和完成证据由持久化状态负责保存。 [长任务的上下文压缩](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)

压缩应回答本轮需要哪些旧信息。压缩后的摘要可以留在会话里，跨任务写入仍需要独立筛选和确认。要校对精确参数、原始证据或工具结果时，按引用回查对应记录。

## 6. 冲突、失效与删除

- **同一范围的更正。** 用逻辑键定位旧记录，保存新版本并标记旧版本失效。后台任务基于旧来源晚到时，按版本校验处理。
- **不同范围的差异。** 项目约定与用户偏好可以并存。读取时根据当前项目和任务选择，避免把局部规则扩成全局事实。
- **随时间变化的事实。** 给这类数据设置核验期限。过期后先重新查询，或以不确定状态提供给模型。
- **撤回信息。** 从可查询范围移除记录，并同步处理相关的搜索索引、缓存和可复用摘要。后台任务重放时要识别已经撤回的版本。

## 7. 怎么判断记忆设计有效

分别验证写入和读取。写入验证哪些事实被归到正确的范围，哪些只应保留在当前会话。读取验证当前任务能取到该用的记忆，过期、撤回或其他用户的信息不会被注入。可以覆盖更正、范围冲突、空结果和并发更新这些路径。

评估任务效果时，可以用同一组任务对照有无记忆的结果，并记录有效召回、错误带入、输入 Token 和额外耗时。如果只是取回了更多历史，却带入了过期信息或增加了成本，应回到写入和筛选条件调整。
