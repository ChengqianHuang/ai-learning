# 3. Agent 与工具调用

Agent 的执行过程包含多次模型决策和外部操作。应用需要维护任务状态、验证执行结果，并管理失败后的重试与恢复。设计时可以把职责划成三层。

| 层 | 职责 |
|---|---|
| 决策 | 模型根据目标和已观察到的结果，提出下一步操作或结束本轮 |
| 执行 | 应用校验调用，管理身份、超时、并发和预算，再访问工具 |
| 状态 | 应用持久化进度，保存外部操作的证据，并决定任务能否恢复 |

## 3.1 Tool Calling 与工具契约

工具调用是一轮往返。应用把当前可用的工具定义发给模型，接收模型返回的工具名、参数和调用 ID。应用校验后执行工具，再把结果与原调用 ID 关联起来，交给模型继续决策。一轮响应可以包含多个调用，应用根据数据依赖和是否修改同一资源来判断能否并行。

| 契约 | 应当定义的内容 |
|---|---|
| 输入 | 参数类型、必填项、标识符含义和合法取值。执行前额外核对资源是否存在、操作前置条件是否满足 |
| 权限 | 以哪个用户或服务身份访问哪个资源。由宿主和目标服务分别执行各自的权限规则 |
| 副作用 | 是否修改外部状态、是否支持并发或取消、是否允许幂等重试 |
| 输出 | 执行状态、结构化结果、外部资源 ID 或错误码。提供足够证据，让应用能判断目标是否达成 |

工具返回的文本、文档和数据是决策输入。运行时把工具权限和执行规则保存在应用层，避免工具结果里的文字改变调用权限或执行预算。工具调用 ID 负责关联一轮请求与响应。跨轮次重试需要单独的业务操作标识，见 3.7。

## 3.2 工作流与 Agent 的选型

工作流以预定义的控制流组织模型和工具，允许条件分支、循环和并行。Agent 把部分控制流交给模型，由模型依据执行反馈动态选择下一步。两者可以组合，边界取决于哪些决策能提前用规则表达，哪些要在运行中根据新信息判断。 [Anthropic 对工作流与 Agent 的区分](https://www.anthropic.com/research/building-effective-agents)

| 决策条件 | 设计取向 |
|---|---|
| 分支固定，输入和成功条件明确 | 用工作流表达顺序、依赖和失败分支，直接验证可预期路径 |
| 只有个别节点需要解释模糊信息或选择策略 | 在工作流中嵌入模型决策，定义节点的输入、输出、工具范围和预算 |
| 执行路径取决于多轮观察，工具组合很难事先穷举 | 用 Agent 决定路径，运行时限制可执行动作并检查完成条件 |

Agent 选型还要看**反馈是否足够**。工具必须能返回让模型区分成功、失败和未知的证据。比较方案时，关注动态决策是否提升最终完成率，以及增加了多少工具调用、延迟和故障恢复成本。

## 3.3 任务规划与进度判定

计划至少表达目标、子任务依赖和可验证的完成条件。显式计划适合多步骤、可暂停的任务。任务短且下一步高度依赖即时反馈时，可以逐步决策，每次只计划可执行的动作。两种方式都需要保留已经确认的结果。

运行时只调度前置条件已满足的步骤。遇到新信息时，先判断该修正参数、重试同一操作，还是重规划后续步骤。重规划时，先读取已经发生的外部变更，再决定哪些步骤需要调整。已执行的副作用需要按目标系统提供的撤销或补偿机制处理。

把**完成条件**和**结束条件**分别写清。完成条件要求可验证的结果或目标状态。预算耗尽、权限不足或结果无法确认也可以结束本轮，此时记录部分完成或阻塞状态，以及恢复所需的条件。

## 3.4 持久化状态、上下文与记忆

| 数据 | 用途 | 保留内容 |
|---|---|---|
| 执行状态 | 恢复任务并核对进度 | 任务与步骤标识、当前状态、尝试次数、操作标识和结果证据 |
| 模型上下文 | 支持这一轮决策 | 目标、剩余约束、相关工具结果和必要历史 |
| 跨任务记忆 | 在后续任务中复用信息 | 已确认的事实或偏好，以及来源、适用范围和更新时间 |

执行状态可建模成状态机。发出调用前保存操作意图，再把步骤标为执行中。收到可信结果后，保存外部结果并推进状态。已发出但结果无法确认的调用进入**待核对**，恢复时先核对外部状态。对同一步骤的并发执行，可以用数据库唯一约束或带版本的条件更新，让一个执行者取得该步骤的处理权。

应用可以压缩历史以控制模型上下文，但应保留恢复所需的原始结果和操作标识。模型只读取本轮决策所需的信息。调用轨迹用于追踪，持久化状态用于恢复，跨任务记忆用于复用，三者的更新规则各自独立。

状态机、持久化时点、超时恢复和并发接管见 [Agent 状态](2.%20Agent%20状态.md)。记忆的形成、检索、压缩与失效见 [Agent 记忆](3.%20Agent%20记忆.md)。

## 3.5 MCP 与工具调用的协议边界

MCP（Model Context Protocol）标准化宿主应用与外部能力的连接。宿主通过 MCP 客户端连接服务端，协商版本和能力。服务端可暴露工具、资源和提示模板。客户端调用 `tools/list` 发现工具，再用 `tools/call` 发送已获准的请求。 [MCP 架构说明](https://modelcontextprotocol.io/docs/learn/architecture)

Tool Calling 是模型和应用之间的结构化调用约定。MCP 是应用和工具服务之间的协议。宿主可以把 MCP 发现的工具描述转换为模型能读取的定义，并把执行结果转换成模型 API 的工具结果。Agent 的规划、任务恢复和幂等策略由宿主或目标服务实现。

处理 MCP 返回值时，保留报错层级。工具不存在或协议请求非法可返回 JSON-RPC 错误。工具执行时的业务错误可以在工具结果里通过 `isError` 表示。应用据此决定下一步，传输成功只表明收到协议响应。 [MCP Tools 规范](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)

## 3.6 工具调用失败与重试

重试策略由运行时根据**故障类别、外部副作用和剩余预算**决定。需要模型修正输入时，给它具体、可处理的错误。可自动恢复的传输故障在执行层处理，避免 SDK、执行层和 Agent 都各自重试，把底层请求数成倍放大。 [超时、退避与抖动](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/)

| 可确认的事实 | 动作 |
|---|---|
| 调用明确被拒绝，操作未执行 | 修正参数、补齐依赖或处理权限。原参数和条件未变化时结束该分支 |
| 可重试故障，操作只读或有明确幂等保证 | 在剩余截止时间内重试。按服务端重试提示等待，或采用有上限的指数退避加随机抖动 |
| 写入已发出，响应超时或连接断开 | 标记结果未知。通过幂等键或外部标识查证，按接口约定重试或等待核对 |
| 已确认部分成功 | 保存已完成的外部变更，只恢复未完成的操作。需要撤销时单独处理并校验结果 |

单次工具调用应有超时，整个任务也应有总截止时间。取消本地等待后，已发出的操作仍可能在远端完成。恢复决策要依据远端结果和接口契约。

## 3.7 防止死循环与重复执行

### 用可观察进展约束循环

运行时在每轮结束后检查完成条件和预算。预算可同时限制总步骤、工具调用数、耗时和成本。无进展检测可以观察目标状态是否变化、是否获取了新证据，或是否完成了新的子步骤。模型改写计划、工具参数略有变动，都需要结合实际状态判断有没有进展。

连续无进展时，终止或挂起当前分支，记录阻塞原因和恢复条件。相同工具、同一目标资源和语义等价的参数可归并为同一种尝试，避免参数换个写法就绕开重试计数。 [Agent 的反馈与停止条件](https://www.anthropic.com/research/building-effective-agents#agents)

### 用业务操作标识约束写入

**一次模型调用、一次请求尝试和一次业务操作有不同的身份。** 同一业务操作可以跨进程、跨模型轮次发起多次请求。首次写入前持久化业务操作标识和参数。在目标服务支持幂等时，为重试传入同一个幂等键和同一份参数，并注意服务端的去重范围、有效期和参数约束。同键遇到不同业务参数时，作为冲突处理。 [幂等 API 与重试](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)

关键故障窗口在 **远端已提交、本地尚未记录结果** 之间。本地锁、唯一约束和事务可以保护本地状态，远端副作用能否去重取决于目标服务。目标服务无法按操作标识核对结果、也缺少幂等保证时，保留「待核对」，避免恢复时盲目重复写入。

## 3.8 可观测性与评估

按任务、步骤和调用记录轨迹，包括工具名称、参数摘要、操作标识、结果分类、外部资源 ID、耗时和终止原因。这样可以把失败定位到模型决策、权限校验、工具执行、结果验证或恢复逻辑。记录参数时应脱敏，并限制持久化内容的范围。

评估时同时检查**最终状态**和**执行轨迹**。先确认目标状态确实成立，再检查过程是否出现重复写入、超预算或越过权限。回归测试可注入超时、部分成功和进程重启，检查恢复后的状态与外部结果。比较工作流和 Agent 时，用相同任务集衡量完成率、调用数、耗时和重复操作率。 [Agent 评估中的执行轨迹与最终结果](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)
