# 1. 大模型基础与调用

本章讲模型怎样处理文本，以及应用怎样调用模型、控制输入和处理输出。调用示例用会议记录演示两种任务。一种是把摘要逐步显示给读者，另一种是把待办整理成程序可读取的 JSON。

## 1.1 Token

Token 是文本经过 Tokenizer 拆分后得到的单位，可以是一个字、一个词、词的一部分或标点。Tokenizer 用词表把每个 Token 映射成一个整数 `Token ID`。一个汉字可能对应多个 Token，同一段文本换一个 Tokenizer，得到的编号和数量也可能不同。

```text
文本 → Tokenizer → Token ID 序列 → Embedding 层查表 → Token 向量序列
```

**Token 数量决定文本占多少输入位置。** 估算请求长度时，使用目标模型的 Tokenizer 或 API 提供的计数接口。聊天请求还可能含有角色标记和特殊 Token，单独数正文会漏掉这些开销。

## 1.2 上下文窗口与输出上限

**上下文窗口**决定模型在一次请求中能处理多少上下文。输入通常包含系统指令、随请求发送的对话历史、当前问题、附带的资料，以及适用时的工具定义和工具结果。多轮对话中，把历史消息再次传入，也会占用输入预算。

**`max_tokens` 是生成上限。** 生成模型逐步预测下一个 Token，推理服务可以在遇到结束标记、达到输出上限或收到取消请求时停止。达到 `max_tokens` 时，回答可能停在句子或 JSON 的中间。部分推理模型的思考 Token 也会消耗输出预算，按具体模型和接口文档计算。

### 上下文过长怎么办

调用前，先按模型规则为生成留空间。例如，模型总窗口是 16,000 Token，计划预留 2,000 Token 给输出，再留 500 Token 余量，那么输入预算约为 13,500 Token。若接口同时设有单独的输入上限，取更严格的限制。

| 占用预算的是 | 怎么处理 |
|---|---|
| 过多附带材料 | 去掉重复内容，优先保留与当前任务直接相关的段落 |
| 过长对话历史 | 保留当前问题、最近几轮和关键约束。把较早历史压成摘要，关键原文按需查回 |
| 必须处理整份长文档 | 例如整理长会议记录，可以按议题分别提取决定和待办，最后合并并去重 |
| 输出被截断 | 检查停止原因。若是输出上限，缩短要求或提高输出预算，重新生成完整结果 |

例如，MiniMax 的 Anthropic 兼容接口提供 `messages/count_tokens` 用于调用前估算输入。把准备发送的系统消息、历史和资料一起计数，再按输入预算判断是否需要删减。 [MiniMax 接口文档](https://platform.minimax.cn/docs/api-reference/text-anthropic-api)

## 1.3 Embedding

Embedding 有两个常见用法。

| 用法 | 输入与输出 | 对应场景 |
|---|---|---|
| 模型内部的 Embedding 层 | 每个 Token ID 查出一个初始向量 | Transformer 的输入准备 |
| 文本 Embedding | 一段文本经过分词和编码，常用池化得到一个向量，再按需要归一化 | 语义相似度、聚类、去重 |

例如，可以用同一个文本 Embedding 模型编码「忘记密码怎么找回」和「重置账户密码」，再比较两个向量。向量分别代表整句文本，维度由模型决定。比较相似度时，常用余弦相似度衡量两个向量的方向有多接近。

## 1.4 Transformer 基础

查表后，每个位置有一个初始向量。模型使用位置信息来区分顺序，再通过多层 Transformer 更新各位置的表示。每层里的自注意力让当前位置参考其他允许看到的位置，前馈网络继续变换每个位置的表示。

自注意力可以用 Q、K、V 理解。当前位置用 `Q` 和其他位置的 `K` 算相关分数，经 softmax 得到权重，再对相应的 `V` 加权求和。比如「共享变量加锁」与「数据库行锁」中的「锁」，即使最初查表得到同一个向量，经过编码也会因周围内容得到不同的表示。

以双向编码器和自回归生成模型为例。双向编码器可以让输入中的 Token 参考左右两侧的信息，文本 Embedding 模型可以进一步将这些表示池化。自回归生成时，模型根据已输入和已生成的 Token 预测下一个 Token，每生成一步就把选中的 Token 加入序列，再继续预测。

```text
编码文本 → Token 上下文向量 → 池化 → 文本向量
生成文本 → 基于已知序列预测下一个 Token → 重复生成 → 答案文本
```

## 1.5 温度参数 `temperature`

在支持温度的生成接口里，温度调整的是**下一个 Token 的采样分布**。对模型输出的分数 `logits`，可以用 `softmax(logits / T)` 理解 `T > 0` 时的效果。

- 温度较低时，概率集中到原本分数较高的候选。同一问题往往得到更接近的措辞，适合事实问答或字段提取。
- 温度较高时，原本分数较低的候选更有机会被选中，适合发散写作。
- `T = 0` 由接口单独定义，通常表示贪心选取或近似确定性解码。应用仍需核对事实与格式，并以该接口的行为为准。

接口支持情况要单独确认。以 MiniMax 的 Anthropic 兼容接口为例，`MiniMax-M3.1-Flash` 固定使用温度 `1`，传入的 `temperature` 会被忽略。`output_config.effort` 调节的是思考深度。 [MiniMax 参数支持表](https://platform.minimax.cn/docs/api-reference/text-anthropic-api)

## 1.6 模型调用与流式输出

模型请求通常指定 `model`、系统提示、用户消息和输出预算。以 Anthropic SDK 为例，使用 `client.messages.create()` 发起非流式请求，等完整响应返回后，从内容块里提取 `text`，再检查 `stop_reason` 和 `usage`。

**流式输出**会在生成过程中把事件增量发给客户端，界面可以收到正文后马上显示。一个增量可能包含半个词或几句话，事件流还可能包括思考、工具调用或错误。服务端真正结束后，再把结果作为完整答案保存。

下面的示例使用 `anthropic` SDK，密钥从 `MINIMAX_API_KEY` 环境变量读取。`text_stream` 只迭代正文增量，`get_final_message()` 返回完整消息，可检查停止原因和用量。 [MiniMax 流式示例](https://platform.minimax.cn/docs/api-reference/text-anthropic-api#流式响应) · [Anthropic SDK 流式说明](https://platform.claude.com/docs/en/build-with-claude/streaming)

```python
import os

from anthropic import Anthropic

with Anthropic(
    api_key=os.environ["MINIMAX_API_KEY"],
    base_url="https://api.minimax.cn/anthropic",
) as client:
    with client.messages.stream(
        model="MiniMax-M3.1-Flash",
        output_config={"effort": "low"},
        max_tokens=2048,
        system="用一句话总结会议记录。",
        messages=[{"role": "user", "content": "小林周三前提交接口草案，团队周五评审。"}],
    ) as stream:
        for delta in stream.text_stream:
            print(delta, end="", flush=True)
        final = stream.get_final_message()

print("\n停止原因", final.stop_reason)
```

## 1.7 结构化输出

结构化输出让程序按约定读取字段。比如提取会议待办时，可以约定 `summary` 是摘要字符串，`tasks` 是待办数组，每条待办包含事项和负责人。

```json
{
  "summary": "周三前提交接口草案，周五评审。",
  "tasks": [{"task": "周三前提交接口草案", "owner": "小林"}]
}
```

| 方式 | 约束程度 |
|---|---|
| 提示词要求返回 JSON | 告诉模型期望格式，应用负责解析和验证 |
| JSON 模式 | 支持时，正常完成的输出遵循 JSON 语法。应用继续校验字段和类型 |
| JSON Schema 结构化输出 | 支持时，传入字段约束，让模型在生成阶段遵循接口支持的 Schema。应用继续校验业务规则 |

Schema 能约束 `tasks` 是对象数组、`owner` 是字符串。负责人是否在参会名单中，需要应用用名单来校验。结构化输出的参数随模型和接口变化。例如 Claude Messages 提供 `output_config.format`。接入 MiniMax 时以其自己的支持表为准。 [Claude 结构化输出](https://platform.claude.com/docs/en/build-with-claude/structured-outputs) · [MiniMax 参数支持表](https://platform.minimax.cn/docs/api-reference/text-anthropic-api)

### JSON 输出不合法如何处理

1. **先看生成是否完成。** 流式请求先拼完正文，再解析一次。达到 `max_tokens` 或发生断流时，先处理截断原因，补足预算或缩短生成要求，再重新发起请求。
2. **区分语法、字段和业务错误。** 缺引号、结尾逗号属于 JSON 语法错误。`"owner": 123` 语法有效，但字段类型错误。`"owner": "小夏"` 类型正确，但如果小夏不在本次参会名单里，就会触发示例的业务校验。
3. **按错误类型做有限重试。** 可以附上具体错误，要求模型重新返回完整对象，并重新执行全部校验。重试预算用完后返回明确错误。展示未经校验的文本时，将它当作预览，业务写入等操作只接收通过校验的对象。

用 Python 做三层检查时，可以先解析语法，再验证类型，最后核对名单。下面的示例假定待办只能分配给本次参会者，并以 `end_turn` 作为单轮模型输出的正常结束状态。

```python
import json

from pydantic import BaseModel, ConfigDict, Field


class ActionItem(BaseModel):
    model_config = ConfigDict(extra="forbid")

    task: str = Field(min_length=1)
    owner: str = Field(min_length=1)


class MeetingNotes(BaseModel):
    model_config = ConfigDict(extra="forbid")

    summary: str = Field(min_length=1)
    tasks: list[ActionItem]


def parse_notes(text: str, stop_reason: str, attendees: set[str]) -> MeetingNotes:
    if stop_reason != "end_turn":
        raise ValueError(f"生成未正常结束：{stop_reason}")
    payload = json.loads(text)  # 语法错误会抛出 JSONDecodeError
    result = MeetingNotes.model_validate(payload, strict=True)  # 字段错误会抛出 ValidationError
    unknown = {item.owner for item in result.tasks} - attendees
    if unknown:
        raise ValueError(f"负责人不在参会名单中：{sorted(unknown)}")
     return result
```
