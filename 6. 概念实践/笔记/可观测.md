# 6. 可观测与 OpenTelemetry

OpenTelemetry（OTel）是一套观测规范。它规定三件事：进程内怎么产生记录（API）、记录成什么结构（数据模型）、怎么把记录发出去（OTLP 协议）。后端用什么存储、怎么查询，不在规范范围内。

观测通常分三个信号：traces、metrics、logs。

| 信号 | 记录什么 | 回答的问题 |
|---|---|---|
| traces | 一次调用经过哪些步骤，每步耗时多久 | 这次请求慢在哪一步、错在哪个环节 |
| metrics | 聚合后的数值，如请求数、错误率、P99 | 整体趋势有没有异常 |
| logs | 离散的文本事件 | 某个时刻具体发生了什么 |

日志只能证明某个时刻发生了什么，无法自动还原「A 调 B、B 调 C」的层次和耗时。trace 补的就是这个结构：一次请求对应一个 trace，每个步骤对应一个 span，span 通过 `parent_span_id` 组成树。

本次只做 traces。用三个脚本走完一条跨进程链路：客户端发起请求，服务端处理，两个进程的 span 发到同一个接收端，拼成一棵树。验证四件事：span 的父子关系、跨进程的上下文传播、错误落在哪个 span、采样之后链路是否完整。

## 6.2 第一步：先写接收端，看 OTLP 长什么样

OTel 的 SDK 默认不把数据写到文件，而是通过 OTLP 协议 POST 到某个地址。默认端口 4318，路径 `/v1/traces`，格式是 protobuf。

写一个最小接收端，就能看到 SDK 实际发出的报文。`receiver.py` 的 POST 处理只有三步：读 body、反序列化、按 trace 分组打印。

```python
body = self.rfile.read(length)
request = trace_service_pb2.ExportTraceServiceRequest()
request.ParseFromString(body)

for resource_spans in request.resource_spans:
    service = service_name(resource_spans.resource)
    for scope_spans in resource_spans.scope_spans:
        for span in scope_spans.spans:
            traces[span.trace_id.hex()].append({"span": span, "service": service})
```

[receiver.py#L96](../otel/receiver.py#L96) 是反序列化，[receiver.py#L109](../otel/receiver.py#L109) 是打印入口，[receiver.py#L52](../otel/receiver.py#L52) 是按 `parent_span_id` 递归成树。

它是 HTTP 服务，要返回一个空的 protobuf 响应，否则 exporter 认为发送失败：

```python
payload = trace_service_pb2.ExportTraceServiceResponse().SerializeToString()
self.send_response(200)
self.send_header("Content-Type", "application/x-protobuf")
self.send_header("Content-Length", str(len(payload)))
```

启动：

```bash
.venv/bin/python receiver.py --raw
```

加 `--raw` 会先用 protobuf 的文本格式打印原始请求。启动后它只打印监听地址，收到第一个 span 才开始输出。

## 6.3 第二步：产生第一个 span

`server.py` 负责建 provider、注册 exporter、生成 tracer：

```python
def build_tracer(exporter):
    provider = TracerProvider(
        resource=Resource.create({
            "service.name": SERVICE_NAME,
            "service.version": "0.1.0",
            "deployment.environment.name": "local",
        })
    )
    if exporter == "console":
        span_exporter = ConsoleSpanExporter()
    else:
        span_exporter = OTLPSpanExporter(endpoint="http://127.0.0.1:4318/v1/traces")
    provider.add_span_processor(SimpleSpanProcessor(span_exporter))
    trace.set_tracer_provider(provider)
    return trace.get_tracer(SERVICE_NAME)
```

[server.py#L20](../otel/server.py#L20) 是这段。三件事各自的作用：

- `Resource` 是进程级属性，会附加到这个进程产生的每个 span 上。`service.name` 是唯一必须给的，后端靠它区分服务。
- `OTLPSpanExporter` 负责序列化和发送，`endpoint` 要写到 `/v1/traces`。
- `SimpleSpanProcessor` 在 span 结束时同步导出。生产环境用 `BatchSpanProcessor`，攒一批再发，避免每个 span 一次网络请求。

任何 HTTP 请求进来时，开一个 SERVER span：

```python
with TRACER.start_as_current_span(
    "POST /analyse",
    context=parent,
    kind=SpanKind.SERVER,
    attributes={
        "http.request.method": "POST",
        "url.path": self.path,
        "http.request.body.size": len(raw),
    },
) as span:
```

[server.py#L64](../otel/server.py#L64)。`kind` 有五个取值，`SERVER` 表示收到请求，`CLIENT` 表示发出请求，`INTERNAL` 表示进程内的步骤。后端靠它区分调用方向。

跑一次请求，接收端打印：

```
trace 605f554e558e8a782f116ac58d7e8c70  spans=1
- [otel-server] POST /analyse  SERVER  2.59ms  OK
    attrs: http.request.method=POST, url.path=/analyse, http.request.body.size=30
```

一行就是一次调用。方括号里是 `service.name`，后面依次是 span 名、kind、耗时、状态。耗时是 `end_time_unix_nano - start_time_unix_nano`，由 SDK 在 span 结束时计算。

`--raw` 模式能看到同样的数据在 protobuf 里的样子：

```
resource_spans {
  resource {
    attributes {
      key: "telemetry.sdk.language"
      value { string_value: "python" }
    }
    attributes {
      key: "service.name"
      value { string_value: "otel-server" }
    }
  }
  scope_spans {
    scope { name: "otel-server" }
    spans {
      trace_id: "\216Gj\022tR\023\353\322\214\005\306\341\342g\274"
      span_id: "\357\t1\022S\311\002\241"
      parent_span_id: "\356\262\266X\022\207\334\321"
      name: "parse_input"
      kind: SPAN_KIND_INTERNAL
      start_time_unix_nano: 1795778294155153000
      end_time_unix_nano: 1795778294155164000
```

三处值得注意：

1. 报文是四层嵌套：`ExportTraceServiceRequest` → `resource_spans[]` → `scope_spans[]` → `spans[]`。resource 一层一个进程，scope 一层一个 tracer。
2. `trace_id` 在报文里是原始字节，不是十六进制字符串。终端看到的 32 位 hex 是消费端转的，比如 `span.trace_id.hex()`。
3. resource 里的 `telemetry.sdk.language`、`telemetry.sdk.name`、`telemetry.sdk.version`、`service.instance.id` 是 SDK 自动加的，业务代码只提供了 `service.name`。

## 6.4 第三步：嵌套 span

一次请求内部往往有多个步骤。每个步骤再开一个 span，就会自动成为当前 span 的子节点，不需要手写 parent。

```python
with TRACER.start_as_current_span("parse_input") as child:
    child.set_attribute("demo.input_chars", len(raw))
    ...
    child.set_attribute("demo.line_count", len(lines))

stats = score_text(lines)
```

[server.py#L75](../otel/server.py#L75) 是 `parse_input`，[server.py#L44](../otel/server.py#L44) 是 `score_text`。`start_as_current_span` 把新 span 设为当前 span，函数返回时自动结束并恢复父 span。

跑一次完整请求，接收端打印：

```
trace 605f554e558e8a782f116ac58d7e8c70  spans=4
- [otel-client] POST /analyse  CLIENT  16.24ms  OK
    attrs: server.address=127.0.0.1, url.full=http://127.0.0.1:8000/analyse,
           http.request.header.traceparent=00-605f554e558e8a782f116ac58d7e8c70-97c7f7eca...,
           http.response.status_code=200
  - [otel-server] POST /analyse  SERVER  2.59ms  OK
      attrs: http.request.method=POST, url.path=/analyse, http.request.body.size=30
    - [otel-server] parse_input  INTERNAL  0.01ms  UNSET
        attrs: demo.input_chars=30, demo.line_count=5
    - [otel-server] score_text  INTERNAL  0.02ms  UNSET
        attrs: demo.line_count=5, demo.word_count=5, demo.has_fence=true, demo.pipeline=["parse", "score"]
```

缩进就是父子关系。两个子 span 的耗时之和小于父 span 的 2.59ms，差额是框架开销。client 的 16.24ms 比 server 的 2.59ms 大，差额是建连、序列化和网络往返。

`demo.pipeline=["parse", "score"]` 在 OTLP 里是 `array_value`，receiver 用 `WhichOneof("value")` 判断类型再展开，[receiver.py#L19](../otel/receiver.py#L19)。

这里有个容易误读的地方：两个 INTERNAL span 的状态是 `UNSET`，不是 `OK`。OTel 里 `UNSET` 表示没有显式设置，不代表失败。只有显式 `set_status(StatusCode.ERROR)` 才表示失败。

## 6.5 第四步：跨进程传播

前面三个 span 在同一个进程里，父子关系靠 context 自动传递。跨进程时 context 传不过去，要靠请求头。

W3C 定义的格式是 `traceparent`：

```
00-605f554e558e8a782f116ac58d7e8c70-97c7f7ecaa112a04-03
```

四段依次是：版本、32 个十六进制字符的 trace_id、16 个十六进制字符的父 span_id、标志位。服务端读到这个头，就能把自己的 span 接到同一个 trace 下面。

客户端注入：

```python
headers = {"Content-Type": "text/plain; charset=utf-8"}
propagate.inject(headers)
traceparent = headers.get("traceparent", "")
```

[client.py#L38](../otel/client.py#L38)。`inject` 读当前 span 的 context，把 `traceparent` 写进传入的 dict。

服务端提取：

```python
carrier = {key.lower(): value for key, value in self.headers.items()}
parent = propagate.extract(carrier)

with TRACER.start_as_current_span("POST /analyse", context=parent, kind=SpanKind.SERVER, ...):
```

[server.py#L61](../otel/server.py#L61) 到 [server.py#L62](../otel/server.py#L62)。

第一行的小写转换是必须的。`TraceContextTextMapPropagator` 用固定的小写键查找，源码里的常量是 `_TRACEPARENT_HEADER_NAME = "traceparent"`，提取时走 `getter.get(carrier, "traceparent")`。传进去的是 dict，`get` 是精确匹配；而 `BaseHTTPRequestHandler.headers` 保留客户端发送的原始大小写，可能是 `Traceparent`。不转换就取不到，服务端会另起一个 trace，两段链路断成两条。

实测跑通后，接收端只有一棵树，client 的 span 是根，server 的 span 是它的子节点：

```
- [otel-client] POST /analyse  CLIENT  16.24ms  OK
  - [otel-server] POST /analyse  SERVER  2.59ms  OK
    - [otel-server] parse_input  INTERNAL  0.01ms  UNSET
    - [otel-server] score_text  INTERNAL  0.02ms  UNSET
```

两个进程各自把 span 发到同一个接收端，接收端按 `trace_id` 归并，按 `parent_span_id` 排序。归并这一步发生在存储侧，不在 SDK 里。

## 6.6 第五步：错误落在哪个 span

可观测的价值在这一步才体现出来：不是知道「请求失败了」，而是知道「失败发生在哪一步」。

服务端有一条会失败的路径。请求正文为空时，`parse_input` 抛 `ValueError`：

```python
with TRACER.start_as_current_span(
    "parse_input",
    record_exception=False,
    set_status_on_exception=False,
) as child:
    child.set_attribute("demo.input_chars", len(raw))
    try:
        lines = parse_input(raw)
        if not lines:
            raise ValueError("输入为空，无法统计")
    except ValueError as exc:
        child.record_exception(exc)
        child.set_status(Status(StatusCode.ERROR, str(exc)))
        raise
```

[server.py#L75](../otel/server.py#L75)。`record_exception` 把异常写成一个 span 事件，包含类型、消息和堆栈。`set_status` 把状态设为 ERROR，第二个参数是状态描述。

抛出的异常继续向上传播，外层 span 也记录一次：

```python
except ValueError as exc:
    span.record_exception(exc)
    span.set_status(Status(StatusCode.ERROR, str(exc)))
    span.set_attribute("error.type", type(exc).__name__)
```

[server.py#L98](../otel/server.py#L98)。

跑 `client.py --empty`，接收端打印：

```
trace 4d817dbcbf95eb80828702ac11ea8833  spans=3
- [otel-client] POST /analyse  CLIENT  13.22ms  ERROR
    attrs: ..., http.response.status_code=400
  - [otel-server] POST /analyse  SERVER  5.33ms  ERROR
      attrs: http.request.method=POST, url.path=/analyse, http.request.body.size=0,
             error.type=ValueError
      event: exception  exception.type=ValueError, exception.message=输入为空，无法统计, ... exception.escaped=False
    - [otel-server] parse_input  INTERNAL  4.26ms  ERROR
        attrs: demo.input_chars=0
        event: exception  exception.type=ValueError, exception.message=输入为空，无法统计, ...
```

三层都是 ERROR，异常事件只出现在真正抛出的那两层。`parse_input` 的 4.26ms 占了 server 5.33ms 的绝大部分，能直接看出时间花在失败路径上。

这里踩了一个坑。第一版的 `start_as_current_span("parse_input")` 没有加那两个参数，结果 `parse_input` 上出现了两条完全相同的 exception 事件。

原因是 SDK 的默认行为：`record_exception=True` 时，如果有异常从 `with` 块逃逸出去，SDK 会自动记一次并设状态。代码里手动记了一次，SDK 又自动记了一次。异常在父 span 里被 `except` 捕获，没有逃逸，所以父 span 只有一条。

修法是显式关闭自动记录：

```python
with TRACER.start_as_current_span(
    "parse_input", record_exception=False, set_status_on_exception=False
) as child:
```

关掉之后事件从两条变成一条，状态描述也由代码控制。

## 6.7 第六步：采样

全量上报在生产上成本太高。采样决定哪些 trace 真的被记录和发送。

客户端配置：

```python
provider = TracerProvider(
    resource=Resource.create({"service.name": SERVICE_NAME}),
    sampler=ParentBased(TraceIdRatioBased(ratio)),
)
```

[client.py#L20](../otel/client.py#L20)。`TraceIdRatioBased(0.5)` 按 trace_id 做确定性判断，同一个 trace_id 在任何进程里算出的结果一样。`ParentBased` 让它优先跟随父 span 的采样决定，只有根 span 才用自己的比率。

跑 20 次，比率 0.5：

```bash
.venv/bin/python client.py --repeat 20 --sample-ratio 0.5
```

客户端统计：

```
10 sampled=False
10 sampled=True
```

接收端日志对比：

```
client 发出 20 条 trace：True 10 / False 10
True 写入日志：10/10
False 写入日志：0/10
True 的 span 数：[4]
```

采样的每条都是完整 4 个 span，丢弃的一条都没写入。这是 `ParentBased` 的作用：如果每个进程独立掷骰子，同一条链路会缺段，树长不全。

traceparent 的标志位也跟着变。采样时是 `03`，丢弃时是 `02`：

```
00-<trace_id>-<span_id>-03    # sampled
00-<trace_id>-<span_id>-02    # not sampled
```

最低位是 sampled 标志 `0x01`，第二位是 random-trace-id 标志 `0x02`。SDK 1.45.2 的 `opentelemetry/trace/span.py:215` 是 `SAMPLED = 0x01`，`:216` 是 `RANDOM_TRACE_ID = 0x02`。服务端看到 `02`，就知道上游已经决定不记录，自己也不用记。

## 6.8 和 Agent 可观测的关系

第 3 章 3.8 要求把失败定位到具体环节：模型决策、权限校验、工具执行、结果验证、恢复逻辑。span 的树形结构正好对应这套分解。

| Agent 环节 | span 设计 |
|---|---|
| 一次任务 | 根 span，`kind=SERVER` 或 `INTERNAL`，带 task_id |
| 一次模型调用 | 子 span，`kind=CLIENT`，属性记 model、输入输出 token 数、耗时 |
| 一次工具调用 | 子 span，`kind=CLIENT`，属性记工具名、参数摘要、结果分类 |
| 一次权限校验 | 子 span，属性记策略名、是否放行 |
| 一次恢复 | 子 span，属性记 checkpoint_id、重放的步骤范围 |

这样定位故障时不用读日志猜，直接看哪个 span 是 ERROR、耗时卡在哪一层。工具调用的参数要脱敏后再进 attribute，堆栈里也可能带路径和密钥。

## 6.9 没做的部分

- metrics 和 logs 两个信号。OTel 有对应的 API 和 exporter，这次只做了 traces。
- baggage。跨进程传业务字段的机制，和 traceparent 走同一套 propagator。
- OTLP/gRPC。默认的 HTTP 绑定够用，gRPC 绑定没验证。
- collector。生产上一般先发到 collector，再由它转发到多个后端，这次是 SDK 直连接收端。
- 后端存储和查询。接收端只在内存里累积，重启即丢。
- tail sampling。需要先收全量再决定采样，依赖 collector。
- 敏感字段脱敏。attribute 里现在会带完整请求路径和 size，没有过滤。
